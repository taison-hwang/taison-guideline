# 기존 기능과 비교

하네스에는 이미 세션 사이에 무언가를 남기는 장치가 여럿 있다. dreaming과 겹치는 것, 겹치지 않는 것, 어느 쪽이 나은지를 적는다. 숫자는 이 하네스를 쓰는 jobtailor 프로젝트에서 잰 값이고, 재는 방법은 [측정](measurement.md)에 있다.

## 먼저 나눠 볼 것: 두 가지 기억

세션 사이에 남길 것은 두 가지다.

- 지금 하는 일: 어떤 작업을 어디까지 했고 다음에 무엇을 하는가.
- 해 보고 알게 된 것: 이 저장소에서는 이렇게 해야 된다, 이렇게 하면 막힌다.

하네스의 장치는 거의 다 앞쪽을 위한 것이다. dreaming은 뒤쪽을 위한 것이다. 그래서 대부분은 겹치지 않는다.

## 장치별 비교

| 기존 장치 | 무엇을 남기는가 | 누가 언제 쓰는가 | dreaming과의 관계 |
| --- | --- | --- | --- |
| 커밋, 상태판, 작업 계획 | 지금 하는 일 | 워커·Orchestrator가 일하면서 | 겹치지 않는다. dreaming으로 바꿀 수 없다 |
| 작업 상태 파일, compact 직전 스냅샷 | 작업 하나의 위치와 결정 | 워커가 일하면서, hook이 compact 직전에 | 겹치지 않는다. dreaming은 일이 끝난 뒤에 돌아서 작업 도중에는 쓸 수 없다 |
| 세션 장부 | 세션이 어떤 파일을 다뤘는가 | Orchestrator가 배정할 때 | 겹치지 않는다 |
| 결정 기록(`decisions.tsv`) | 갈림길, 판정, 되돌림, 틀린 보고 사례 | Orchestrator만, 일하면서 | 일부 겹친다. 아래 1 |
| 개발 과정 기록(`docs/progress`) | 조사, 경과, 검증 결과 | 워커·검증자가 일하면서 | 일부 겹친다. 아래 2 |
| `AGENTS.md`의 프로젝트 규칙 | 검사 명령, 실행 방법, 함정 | 사람이 직접 | 겹친다. 아래 3 |
| Claude Code 자동 메모리 | 사용자의 지적과 선호 | Claude 세션이 일하면서 | 일부 겹친다. 아래 4 |
| 독립 검증 기록, 판정 목록 | 작업별 결함과 재현 명령 | 검증 서브에이전트 | 겹치지 않는다. dreaming의 좋은 재료다 |
| `index.md` 먼저 읽기 | 문서 찾는 길 | 문서를 쓰는 세션 | 같은 방식이다. dreaming의 `_index.md`가 이미 있는 셈이다 |
| `herdr-usage`, `herdr-flow` | 토큰과 대기 시간 | 사람이 볼 때 | 겹치지 않는다. 숫자만 있고 내용은 없다 |

### 1. 결정 기록

jobtailor의 결정 기록은 사흘 동안 298줄(125KB)이 쌓였다. Orchestrator가 본 것은 잘 남는다. 예를 들어 새 worktree에 `node_modules`가 없어 보고 관문이 실패한 일은 두 번 적혔다(2026-11-09 17:37, 2026-11-10 00:58). 이 일은 두 번째 기록 한 시간 반쯤 뒤에 커밋으로 고쳐졌다.

약점은 세 가지다.

- Orchestrator에게 보고된 것만 남는다. 워커가 혼자 겪고 넘어간 일은 들어가지 않는다. zsh에서 `echo ====`가 오류를 내는 일은 159개 세션 중 78개에서 생겼지만 결정 기록에는 없다.
- 거의 읽히지 않는다. 쓰기 약 239번에 읽기는 20번이다. 워커가 읽은 것은 2번뿐이다.
- 쌓이기만 한다. 줄을 고치지 않는 규칙이라 정리본이 없다. 위 `node_modules` 건도 첫 기록은 "3회 반복"으로 세고 후속 기록으로만 남겼다. 일곱 시간 뒤 두 번 더 나고서야 고칠 작업 후보가 됐다.

dreaming이 나은 점은 보고되지 않은 일까지 대화 기록에서 건지고, 겹친 내용을 합친다는 것이다. 결정 기록이 나은 점은 그 자리에서 바로 적히고, 사람의 결정과 그 근거가 정확히 남고, 돈이 거의 들지 않는다는 것이다. 사람이 정한 결정의 기록은 결정 기록이 맡아야 한다. dreaming 자료도 지나가는 말이 사람의 결정을 뒤집지 못한다고 정해 두었다.

### 2. 개발 과정 기록

`docs/progress`에는 dreaming과 같은 생각이 이미 규칙으로 있다. 같은 주제는 최근 기록이 이기고, 바꿀 때는 `supersedes`로 가리키고, 에이전트의 기록은 사용자 결정을 뒤집지 못하고, 기록이 쌓이면 `type: snapshot`으로 정리한다.

차이는 정리를 누가 하느냐다. 하네스는 일하는 세션이 틈을 내서 해야 하고, dreaming은 정리자가 따로 돈다. jobtailor의 기록 99개 중 정리본(`snapshot`)은 0개다. 규칙은 있는데 아무도 하지 않았다.

### 3. `AGENTS.md`의 프로젝트 규칙

모든 세션이 시작할 때 읽으므로 가장 확실하게 전해진다. 대신 사람이 찾아서 적어야 한다. jobtailor에는 2026-11-11에 워커 세션을 손으로 재서 넣은 "다시 겪은 함정" 한 줄이 있다. 함정 일곱 가지를 담았다(ruff의 한글 줄 길이, zsh, 임시 스크립트 이름, 뮤테이션 시간, macOS sed 등). 하네스의 `worker.md`에도 같은 날 손으로 찾은 함정 여섯 가지가 네 줄에 걸쳐 들어갔다.

이 손 작업은 dreaming이 하는 일을 사람이 한 것이다. 시험 실행에서 dreaming은 2026-11-09 하루치 기록만 보고 이 13가지 가운데 11가지를 스스로 찾았다([측정](measurement.md)의 "손으로 찾은 함정과 대조").

dreaming이 나은 점은 사람이 재지 않아도 나온다는 것이다. 프로젝트 규칙이 나은 점은 사람이 고른 것만 들어가고, 짧고, 틀린 줄이 섞일 일이 적다는 것이다. 둘은 경쟁하지 않는다. dreaming이 후보를 찾고 사람이 골라 프로젝트 규칙에 넣는 순서가 맞다.

### 4. Claude Code 자동 메모리

형식은 dreaming의 메모와 거의 같다. 자동 메모리도 작은 파일 여러 개, 맨 앞의 이름·설명, `[[이름]]` 링크, 목차 파일(`MEMORY.md`)로 이루어진다. 목차는 세션마다 자동으로 읽힌다(앞 200줄 또는 25KB).

하지만 담는 것이 다르다. 공식 문서는 자동 메모리가 코드에서 알 수 있는 것과 디버깅으로 고친 내용을 적지 않는다고 밝힌다. jobtailor의 자동 메모리는 12개인데 모두 사용자의 지적(feedback)이다. 4개는 같은 주제(서브에이전트 effort)를 다시 적은 것이고, 2026-11-07 뒤로는 새 글이 없다.

| | 자동 메모리 | dreaming |
| --- | --- | --- |
| 쓰는 때 | 일하는 도중, 세션이 스스로 | 끝난 뒤, 다른 에이전트가 |
| 근거 | 세션이 기억하는 것 | 대화 기록의 도구 실행 결과 |
| 담는 것 | 사용자 지적, 선호, 진행 중인 일 | 명령, 값, 함정, 실패한 시도 |
| 겹친 글 | 그대로 쌓인다(12개 중 4개) | 정리자가 합친다 |
| 읽는 쪽 | Claude 세션만 | 파일이므로 Claude·Codex 모두 |
| 읽히는 방식 | 목차가 세션마다 자동으로 들어간다 | 필요할 때 목차부터 연다(자료의 권고) |

jobtailor는 Commander와 검증자가 Codex다. 자동 메모리는 Codex 세션에 닿지 않는다.

## 기존 장치가 놓치는 것

위를 합치면 지금 어디에도 남지 않는 것은 **워커와 검증자가 일하다가 스스로 알아내고 보고하지 않은 것** 한 가지다.

- 워커가 `/clear`될 때 작업 상태는 git과 상태판에 남지만, 일하는 법은 남지 않는다.
- 검증 서브에이전트는 매번 새 맥락으로 뜬다. 지난 검증에서 쓴 방법을 다음 검증이 모른다.
- 결정 기록은 Orchestrator가 본 것만 담는다.
- 자동 메모리는 이런 내용을 일부러 적지 않는다.

dreaming이 기존 장치보다 분명히 나은 곳은 여기 하나다. 나머지에서는 기존 장치가 낫거나 같다.
