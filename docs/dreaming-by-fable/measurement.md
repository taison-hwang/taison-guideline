# 측정

dreaming을 우리 하네스에 대 보려고 잰 값이다. 측정일은 2026-11-11이다.

## 대상

이 하네스를 쓰는 jobtailor 프로젝트의 기록을 쟀다. 기록은 모두 읽기만 했고, 시험 실행의 결과물은 세션 스크래치패드에만 썼다.

| 재료 | 양 | 위치 |
| --- | --- | --- |
| Claude Code 대화 기록 | 159개 파일(에이전트 응답이 있는 세션은 158개), 2026-10-31~11-10(UTC), 원본 637MB | `~/.claude/projects/<프로젝트>/*.jsonl` |
| 결정 기록 | 298줄, 125KB, 2026-11-09~11 | `docs/status/decisions.tsv` |
| 개발 과정 기록 | 99개, 그중 검증 기록 64개 | `docs/progress/` |
| 인계 폴더 | 파일 493개, 32MB | `~/.claude/herdr/handoff/jobtailor/` |
| Claude 자동 메모리 | 12개 | `~/.claude/projects/<프로젝트>/memory/` |

- jobtailor의 하네스는 2026-11-09 판(`e4d31ec`)이다. 세션 장부(`sessions.tsv`)와 보고 기록(`reports.tsv`)이 없다. 그래서 역할은 hook이 넣은 `[herdr 역할]` 글과 배정 메시지에서 읽었고, 작업 경계는 `[배정]` 글로 잘랐다.
- Codex 세션(Commander와 일부 검증자)은 재지 않았다. 아래 숫자는 Claude 세션만의 값이다.

## 1. 세션은 얼마나 크고 얼마나 드는가

대화 기록에서 사람 글, 에이전트 글, 도구 호출과 결과만 남기면(아래에서는 "간추린 기록") 57MB다. 원본의 9%다.

| 역할 | 세션 수 | 간추린 기록(중앙값 / 상위 10% / 최대) | 맥락 최대(중앙값) | 비용 합계 |
| --- | --- | --- | --- | --- |
| 워커 | 31 | 500KB / 1.2MB / 3.3MB | 285k 토큰 | $567 |
| 검증자 | 34 | 142KB / 200KB / 291KB | 128k 토큰 | $72 |
| Orchestrator | 12 | 631KB / 1.2MB / 1.5MB | 311k 토큰 | $295 |
| 그 밖(역할 없는 세션, 옛 하네스의 역할) | 81 | | | $952 |

- 비용은 Claude Code가 기록에 남긴 값(`cost-state`)이다. API 단가로 환산한 값이라 구독으로 쓰면 실제 청구액이 아니다. 전체 합계는 $1,886이다.
- 간추린 기록의 71%는 Bash 호출과 그 결과다(결과 50%, 입력 21%). 에이전트가 쓴 글은 6%다.

뜻: 자료의 예제는 세션 하나가 평균 240KB쯤이고 분석기 하나가 세션 하나를 읽는다. 우리 워커 세션은 그 두 배가 넘고 큰 것은 열 배가 넘는다. dreaming에 넣으려면 세션이 아니라 작업 단위로 잘라야 한다.

## 2. 같은 실수가 되풀이되는가: 도구 오류

오류로 표시된 도구 결과와 끝 코드가 0이 아닌 Bash 결과를 셌다.

| 항목 | 값 |
| --- | --- |
| 도구 호출 | 16,622번 |
| 오류 | 318번(1.9%) |
| 서로 다른 오류 모양 | 219가지 |
| 세션 3개 이상에서 나온 모양 | 18가지, 오류 100번 |
| zsh에서 `echo ====` 같은 줄이 오류를 낸 세션 | 159개 중 78개 |

다음 날로 넘어가는지도 봤다. 2026-11-10에 시작한 역할 세션의 오류 68건 중 34건(50%)은 11-09까지 이미 나온 모양이다. 그 34건 중 20건이 zsh의 `====` 하나다.

뜻: 도구 오류는 적고, 되풀이되는 것은 대부분 사소한 한 가지다. 오류를 줄이는 것만으로는 dreaming을 돌릴 까닭이 되기 어렵다. 다만 11일 동안 세션의 절반이 같은 실수를 했는데도 아무 장치도 이를 잡지 못했다는 것은 분명하다.

## 3. 같은 실수가 되풀이되는가: 검증에서 걸린 결함

`docs/progress`의 검증 기록 64개를 서브에이전트(Sonnet)가 모두 읽고 차단 결함을 뽑아 종류를 붙였다. 수는 스크립트로 셌고, 결함 5개를 원문과 대조해 인용이 맞는지 확인했다.

| 항목 | 값 |
| --- | --- |
| 판정 | ISSUES 38, PASS 26 |
| 검증받은 작업 | 29개 |
| 한 번에 통과한 작업 | 13개(45%) |
| 두 번 이상 걸린 작업 | 15개(2번 6, 3번 3, 4번 3, 5번 2, 7번 1) |
| 차단 결함 | 47개 |
| 같은 작업의 뒤쪽 검증에서 같은 종류가 다시 지적된 것 | 24개 |
| 앞선 다른 작업에 이미 나온 종류 | 15개(32%) |
| 작성자의 테스트가 그 입력을 다루지 않았다고 기록에 적힌 것 | 19개(40%) |

- 다른 작업에서 되풀이된 종류는 넷이다. 그중 가장 큰 "입력 형식·경계 변형을 처리하지 않음"(18개)은 네 작업 모두 추출한 항목을 원문의 제목·목록·표에 붙이는 규칙이었다. 다른 영역으로 옮겨지는지는 이 자료로 알 수 없다.
- 종류 이름은 다 읽은 뒤에 붙였다. 이름을 어떻게 붙이느냐에 따라 "되풀이" 수가 달라진다.
- 작업들이 나란히 돌았을 수 있어서, 앞 기록이 뒤 작업에 전해질 수 있었는지는 따지지 않았다.

뜻: 재작업은 많다(작업의 절반이 두 번 이상 검증). 그 재작업의 절반은 한 작업 안에서 생긴다. 그 워커는 맥락을 들고 있고 앞 판정 기록도 받으므로, 세션 사이 기억이 모자라서 생긴 일이 아니다. 메모로 줄일 수 있는 몫은 많아야 3분의 1이고, 그마저 한 영역에 몰려 있다.

## 4. 기존 기록은 쓰이고 있는가

대화 기록의 도구 호출에서 각 기록 파일을 읽은 횟수와 쓴 횟수를 셌다. Bash 명령에서는 `cat`·`grep` 등을 읽기로, `>>`·`tee` 등을 쓰기로 쳤으므로 대략의 값이다.

| 기록 | 읽기 | 쓰기 | 비고 |
| --- | --- | --- | --- |
| `decisions.tsv` | 20번(9개 세션) | 약 239번 | Orchestrator 18번, 워커 2번 읽음 |
| `docs/progress` | 272번(55개 세션) | 약 267번 | 99개 중 정리본(`snapshot`) 0개 |
| 상태판·작업 계획 | 114번 | 약 356번 | |
| 인계 폴더 파일 | 908번(139개 세션) | 약 1,030번 | 배정·보고 글 |
| Claude 자동 메모리 | 직접 읽기 3번 | 24번 | 목차는 세션마다 자동으로 들어간다 |

Claude 자동 메모리 12개는 모두 `feedback` 유형이다. 4개가 같은 주제(서브에이전트 effort)이고, 마지막으로 쓴 날은 2026-11-07이다.

일하면서 이런 기록에 쓴 글은 모두 합쳐 약 3.9MB다. 에이전트가 화면에 쓴 글 전체(3.7MB)와 비슷하다.

## 5. 시험 실행: dreaming을 그대로 돌려 보기

자료의 분석기·정리자 프롬프트를 고치지 않고(경로만 바꿔) 이 컴퓨터에서 돌렸다.

- 재료: 2026-11-09(UTC)에 시작한 워커·검증자 세션 21개. 간추린 기록 7.1MB, 이 세션들이 쓴 비용은 API 단가로 $138이다.
- 자르기: `[배정]` 글에서 다음 `[배정]`까지를 한 단위로 했다. 한 단위가 260KB를 넘으면 더 잘랐다. 도구 입력과 결과는 하나에 3,500자를 넘으면 앞뒤만 남겼다. 결과는 56개 단위, 5.4MB다(중앙값 87KB, 최대 281KB).
- 실행: 단위마다 `claude -p --model haiku`를 하나씩, 다섯 개씩 동시에 돌렸다. 쓸 수 있는 도구는 읽기·쓰기·고치기·파일 찾기·글 찾기 다섯 개다. 셸, 웹, MCP는 주지 않았다.
- 자료와 다른 점: 리드 에이전트 없이 셸 스크립트가 분석기를 띄웠다. 메모리 저장소 대신 스크래치패드의 폴더를 썼다.

### 손으로 찾은 함정과 대조

2026-11-11에 사람이 워커 세션을 재서 규칙에 넣은 함정이 13가지 있다. 하네스 `worker.md`의 6가지와 jobtailor `AGENTS.md`의 7가지다. 시험 실행의 메모는 그보다 앞선 2026-11-09 하루치 기록만 보고 만들었다. 메모에 같은 내용이 있는지 낱말로 찾고, 걸린 줄을 읽어 확인했다.

| 함정 | 메모에 있는가 |
| --- | --- |
| `herdr-report`를 뒤에서 돌리면 보고 없는 턴으로 센다 | 있다 |
| `herdr-report`를 `timeout`으로 감싸면 보고가 사라진다 | 있다 |
| 상태판 커밋 때문에 빨리 감기 병합이 자주 실패한다 | 있다 |
| `core.hooksPath`로 커밋 검사를 건너뛴다 | 있다 |
| ruff 줄 길이에서 한글 줄이 넘친다 | 있다 |
| zsh에서 맞는 파일이 없는 glob은 명령을 멈춘다 | 있다 |
| zsh는 변수를 낱말로 나누지 않는다 | 있다 |
| 임시 스크립트에 표준 모듈 이름(`struct.py`)을 쓰면 안 된다 | 있다 |
| `make mutate-changed`는 오래 걸려 뒤에서 돌린다 | 있다 |
| macOS `sed -i`가 다르게 동작한다 | 있다 |
| 병합 출력을 `| tail`로 넘기면 실패가 가려진다 | 있다 |
| `sleep N; 명령`은 도구가 막는다 | 없다(기다리는 법만 있다) |
| `python3 -I`는 `PYTHONPATH`를 버린다 | 없다 |

13가지 중 11가지가 메모에 있다. 손 측정은 11-10까지의 세션을 봤을 수 있으므로, 없는 2가지는 11-09 기록에 아예 없던 일일 수 있다.

메모에는 손 측정에 없는 것도 있었다. 새 worktree에 `server/.venv`가 없으니 메인 체크아웃의 것을 상대 경로로 쓴다, `herdr-report`는 셸 명령이라 도구로 부르지 않는다, `connect()`에는 문자열 대신 `Path`를 준다 등이다.

### 다음 날 오류와 대조

2절의 2026-11-10 오류 68건을 메모와 견줬다. 메모에 피하는 법이 적혀 있던 것은 28건(41%)이다. zsh의 `=` 풀이 21건, macOS sed 3건, 빨리 감기 병합 실패 2건, 문자열 경로 1건, `herdr-report`를 도구로 부른 것 1건이다. 21건이 한 가지 실수이므로 여러 실수를 고루 막았다고 보기는 어렵다.

## 6. 시험 실행: 범위를 좁혀 다시 돌리기

5절의 메모는 대부분 기능 상태와 작업 경과였다. 그래서 같은 56개 단위를 한 번 더 돌렸다. 바꾼 것은 프롬프트의 "이번 실행의 선호" 자리 하나다. 자료의 프롬프트에 원래 있는 자리이고, 거기에 아래 뜻의 글을 넣었다.

- 적을 것은 이 저장소에서 일하는 법(명령, 환경, 함정, 걸리는 시간, 검사·병합·검증·보고 절차에서 겪은 문제), 헛돈 시도와 고친 방법, 결함이나 검증 지적에서 나온 다른 작업에도 통할 교훈이다.
- 적지 않을 것은 제품 코드의 동작, 기능·스키마·데이터의 상태, 작업별 경과, 커밋별 진행, 판정과 재생 수치다.

### 좁힌 메모에 무엇이 들었는가

5절과 같은 방법으로 정리 전 메모에서 90줄을 뽑아 분류했다.

| 항목 | 그대로(5절) | 범위를 좁힘 |
| --- | --- | --- |
| 일하는 법 | 32줄 | 65줄 |
| 다른 작업에 옮길 교훈 | 6줄 | 15줄 |

| 새 세션에 쓸모가 있다고 본 줄 | 24줄 | 41줄 |

- 종류는 뜻대로 바뀌었다. 일하는 법과 교훈이 90줄 중 38줄에서 80줄로 늘었다.
- 62줄(69%)은 이미 다른 곳에 있던 내용이다. 26줄은 시작 지침에 있었다. 지침에 한 문장으로 있는 것을 메모가 명령과 숫자까지 풀어 적은 경우가 많다(일부만 적혀 있던 것 40줄).
- 대화 기록에만 있던 28줄 중 기준 시점 앞의 일은 18줄이다. 일하는 법 14줄, 교훈 3줄, 경과 1줄이다. 분류기는 이 가운데 2줄만 "쓸모가 있다"로, 나머지 대부분을 "있을 수도 있다"로 봤다. 일반적인 셸 요령이나 그 작업에서만 쓴 측정 방법이 많았기 때문이다.
- 틀린 줄이 3줄 나왔다. 확인한 42줄의 7%다.
  - 메모가 쓰라고 한 대안이 듣지 않는다. `glob("*.json")` 대신 `glob("[0-9]*.json")`을 쓰라고 했는데, 이것도 피하려던 `6.meta.json`에 맞는다.
  - 이유가 틀렸다. `git worktree remove`에 `--force`가 필요한 까닭을 무시된 파일 때문이라고 적었다.
  - 하네스 규칙과 어긋난다. 옛 진행 기록 맨 위에 정정 글을 넣으라고 했는데, 스킬은 기존 기록을 고치지 말고 새 기록에 `supersedes`를 달라고 한다. 워커가 실제로 한 일을 메모가 지침처럼 적었다.
- 앞의 두 줄은 내가 같은 명령을 돌려 다시 확인했다.
- 두 분류는 따로 돌린 분류기가 했다. "쓸모" 판단의 잣대가 조금 다를 수 있어서, 그 줄 수를 그대로 견주면 안 된다.

뜻: 범위를 좁히면 군더더기는 걸러진다. 그래도 메모의 3분의 2는 지침과 기록에 이미 있는 내용이고, 새로 건진 줄은 자잘하며, 틀린 줄이 섞인다. 세 번째 틀린 줄은 dreaming의 약한 곳에서 나왔다. 분석기는 세션이 한 일을 본 대로 적을 뿐, 그 일이 규칙에 맞았는지는 따지지 않는다.

## 8. 재지 못한 것

- **메모가 다음 세션을 돕는가.** 가장 중요한 물음인데 재지 못했다. 메모를 준 세션과 안 준 세션에 같은 작업을 시켜 견줘야 한다. 이번 측정은 "메모에 그 내용이 있다"까지만 본다. dreaming 자료에도 이 수치는 없다.
- **Codex 세션.** jobtailor의 Commander와 일부 검증자는 Codex다. 이 세션들은 읽지 않았다.
- **다른 프로젝트, 다른 날.** 프로젝트 하나의 하루치로 시험했다. 같은 기록으로 두 번 돌렸을 뿐, 날을 바꿔 되풀이하지 않았다.
- **메모가 여러 날 쌓일 때.** 분석기는 빈 폴더에서 시작했다. 이미 있는 메모를 대조해 고치는 단계(자료의 "확인")는 같은 날의 분석기끼리만 겪었다.
- **메모의 정확도 전체.** 두 표본에서 일하는 법으로 분류된 97줄만 확인했다(62줄 맞음, 3줄 틀림, 32줄 확인 못 함). 나머지 종류는 확인하지 않았다.
- **끼어든 글.** 대화 기록에 지시문을 심어 메모로 옮겨지는지는 시험하지 않았다.
- **손으로 찾은 함정과의 대조.** 사람이 잰 세션과 분석기가 읽은 세션이 겹친다. 같은 재료에서 같은 것을 찾는지 본 것이지, 앞날을 맞히는지 본 것이 아니다.

숫자를 읽을 때 조심할 점도 있다.

- 비용은 모두 API 단가로 환산한 값이다. 구독으로 쓰면 청구액이 아니라 사용량 한도에서 빠진다.
- 실행 환경이 자료와 다르다. 리드 에이전트가 없고, `claude -p`에 자료의 프롬프트를 시스템 프롬프트로 넣었고, 20개가 아니라 5개씩 동시에 돌렸다.
- 결함 종류(3절)와 메모 줄 분류(5절)는 모델이 판단했다. 일부만 사람이 다시 확인했다.
- 읽기·쓰기 횟수(4절)는 명령 글자를 보고 센 어림값이다.
