# 적용 시 장단점

[적합한 부분](fit.md)에서 고른 방식, 곧 묶음이 끝난 뒤 워커·검증자 기록을 읽는 회고를 넣었을 때의 장단점이다. 숫자는 [측정](measurement.md)에서 가져왔다.

## 장점

| 장점 | 내용 | 근거 |
| --- | --- | --- |
| 보고되지 않은 것을 건진다 | 워커가 혼자 겪고 넘어간 함정이 메모에 남는다 | 손으로 찾은 함정 13가지 중 11가지를 하루치 기록에서 찾았다. 범위를 좁힌 실행은 12가지 |
| 일하는 세션을 건드리지 않는다 | 워커가 일하다 말고 기록을 쓰지 않아도 된다. 워커의 맥락과 토큰을 쓰지 않는다 | 분석은 Haiku가 뒤에서 한다 |
| 싸다 | 읽은 세션이 쓴 돈에 견주면 작다 | 워커·검증자 21개 세션(API 단가로 $138)의 기록을 읽는 데 분석기 $5.96, 정리자 $0.79 |
| 도구를 가리지 않는다 | 메모가 파일이라 Claude와 Codex가 함께 읽는다 | Claude 자동 메모리는 Codex 세션에 닿지 않는다 |
| 정리가 실제로 된다 | 겹친 글을 합치는 일을 따로 도는 정리자가 맡는다 | 하네스의 정리 규칙(`type: snapshot`)은 99개 기록 중 0번 쓰였다 |
| 하네스를 고칠 재료가 나온다 | 규칙의 전제와 제거 시험에 쓸 사례가 모인다 | `herdr-report`를 뒤에서 돌리거나 `timeout`으로 감싼 사례를 스스로 찾았다 |
| 세션을 가로질러 본다 | Orchestrator가 `/clear`되어도 되풀이를 센다 | `node_modules` 문제는 다섯 번 겪고서야 고칠 후보가 됐다 |

## 단점과 위험

| 단점 | 내용 | 근거 | 줄이는 방법 |
| --- | --- | --- | --- |
| 그대로 쓰면 군더더기가 대부분이다 | 자료의 프롬프트는 기록에 나온 사실을 다 적는다. 코드 프로젝트에서는 기능 상태와 작업 경과가 대부분을 차지한다 | 하루치에 메모 37개, 476KB, 사실 줄 1,558개. 뽑아 본 90줄 중 새 세션에 쓸모가 있고 다른 곳에 없던 줄은 7줄 | 분석기 범위를 일하는 법과 실패로 좁힌다. 내용은 바뀌지만 양은 385KB로 조금만 준다 |
| 목차가 금방 커진다 | 목차가 길면 여는 것만으로 토큰이 든다 | 하루 만에 목차 16.8KB. 범위를 좁히고 정리자를 돌려도 6.9KB. 자료의 자동 주입 상한 4,096자를 넘는다 | 자동으로 넣지 않는다 |
| 틀린 줄이 섞인다 | 분석기는 세션이 한 일을 본 대로 적는다. 그 일이 맞았는지, 규칙에 맞는지는 따지지 않는다 | 범위를 좁힌 메모에서 확인한 42줄 중 3줄이 틀렸다. 하나는 하네스 규칙과 어긋나는 행동을 지침처럼 적었다 | 메모를 지침으로 쓰지 않는다. 사람이 고른 줄만 지침에 올린다 |
| 이미 있는 내용을 다시 적는다 | 지침과 기록에 있는 것을 메모가 더 길게 풀어 적는다 | 범위를 좁힌 메모 90줄 중 62줄이 이미 다른 곳에 있었다. 26줄은 시작 지침에 있었다 | 분석기에게 지침 파일을 함께 주고, 거기 없는 것만 적게 한다(시험하지 않았다) |
| 낡는다 | 코드가 바뀌면 메모가 틀려진다. 분석기는 마지막 기록 뒤의 일을 모른다 | 자료도 중요한 사실은 다시 확인하라고 한다 | 메모는 단서로만 쓴다. 하네스의 "문서는 단서, 코드로 확인" 규칙을 그대로 적용한다 |
| 끼어든 글이 퍼질 수 있다 | 대화 기록에는 웹 페이지와 도구 출력이 들어 있다. 거기 섞인 지시문이 메모로 옮겨지면 여러 세션이 읽는다 | 자료가 직접 경고한다 | 분석기는 파일 도구만 쓰고, 읽는 세션은 메모를 고치지 못하게 하고, 세션 시작 때 자동으로 넣지 않는다 |
| 비밀이 옮겨질 수 있다 | 대화 기록에 키나 토큰이 찍혀 있을 수 있다 | 시험 실행 메모에서는 키 모양의 문자열이 걸리지 않았다(패턴 검사) | 메모를 저장소에 커밋하지 않고 handoff 폴더에 둔다. 커밋하려면 사람이 먼저 읽는다 |
| 사람 검토가 없다 | 자료의 기본 설정은 밤에 쓴 메모가 다음 날 그대로 쓰인다 | 하네스는 범위·규칙 변경에 사용자 승인을 요구한다 | 지침 파일로 올리는 것은 사용자가 정한다 |
| 효과가 증명되지 않았다 | dreaming 자료에는 다음 세션이 나아졌다는 수치가 없다. 우리 측정도 "찾아낸다"까지만 쟀다 | [측정](measurement.md)의 "재지 못한 것" | 제거 시험을 붙여 넣는다. 아래 "넣는다면 붙일 시험" |
| 턴이 많아 토큰을 많이 쓴다 | 분석기가 턴마다 읽은 기록을 다시 보낸다 | 분석기 하나에 평균 23턴, 캐시 읽기 합계 4,175만 토큰 | 작업 단위를 작게 자르고, 긴 도구 출력은 잘라서 넘긴다 |
| 긴 세션을 잘라야 한다 | 하네스 세션은 길다. 자료의 세션 하나에 분석기 하나는 맞지 않는다 | 워커 세션 기록 중앙값 500KB, 최대 3.3MB | `[배정]` 경계로 자른다 |
| Codex 기록은 따로 읽어야 한다 | 기록 형식이 다르다 | jobtailor는 Commander·검증자가 Codex다 | `herdr-usage`가 두 형식을 이미 읽는다. 같은 읽기 코드를 쓴다 |
| 장치가 하나 는다 | 명령, 프롬프트, 메모 폴더, 읽는 규칙이 더해진다 | 하네스는 필요 없어진 규칙을 지우는 쪽이다 | 수동 실행 하나로 시작하고, 효과가 없으면 뺀다 |
| 검증의 독립성을 해칠 수 있다 | 검증자가 메모를 읽으면 앞 판단에 묶인다 | 하네스는 검증자에게 `[배정]` 원문만 준다 | 검증 서브에이전트에는 메모를 주지 않는다 |

## 넣는다면 붙일 시험

`rules-and-enforcement.md`의 형식으로 적는다.

| 규칙 | 강제 수단 | 전제 | 제거 시험 |
| --- | --- | --- | --- |
| 묶음이 끝나면 워커·검증자 기록으로 회고를 돌려 되풀이 목록과 작업 메모를 만든다 | 실행 명령, Orchestrator 8절 문구 | 보고되지 않은 시행착오가 다음 세션에서 되풀이된다(zsh 실수 78개 세션, `node_modules` 5회) | 메모를 준 묶음과 안 준 묶음에서 같은 함정의 재발 수와 도구 오류 수를 견준다. 되풀이 목록에서 실제로 검사·hook이 된 항목 수를 센다. 두 묶음 연속 0이면 뺀다 |

## 하지 않는 편이 나은 것

- 메모를 세션 시작 hook으로 모든 세션에 넣기. 토큰이 매 턴 들고, 틀린 줄과 끼어든 글이 모든 세션에 간다.
- 메모를 `AGENTS.md`나 스킬에 자동으로 써넣기. 사용자 승인 원칙과 부딪힌다.
- 기능 상태를 메모로 남기기. 코드와 테스트가 기준이고, 메모가 틀리면 틀린 쪽을 믿게 된다.
- 매일 밤 자동 실행. 하네스는 사용자가 목표를 줄 때만 돈다. 묶음 끝이 더 맞는 때다.
