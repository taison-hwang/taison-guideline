# 적용하기 가장 적합한 부분

dreaming을 하네스의 어디에 쓰면 맞는지 후보를 놓고 가렸다. 근거 숫자는 [측정](measurement.md), 기존 장치와의 겹침은 [기존 기능과 비교](compare-existing.md)에 있다.

## 답

가장 맞는 곳은 **묶음이 끝난 뒤의 회고**다. 끝난 작업의 워커·검증자 대화 기록을 읽어, 보고되지 않은 시행착오와 되풀이된 실수를 찾아낸다.

회고 결과는 되풀이 목록과 작업 메모로 쓴다.

1. 되풀이 목록. Orchestrator와 사용자가 읽는다. 여기서 지침·검사·스크립트·hook으로 막을 후보를 고른다. 먼저 이것부터 쓴다.
2. 작업 메모. 이 저장소에서 일하는 법(명령, 환경, 함정)만 담는다. 워커가 필요할 때 목차부터 열어 본다. 메모가 실제로 세션을 돕는지 잰 뒤에 쓴다.

기능의 현재 상태나 작업 경과를 메모로 남기는 것, 메모를 모든 세션에 자동으로 넣는 것은 맞지 않는다.

## 후보와 판단

| 후보 | 무엇을 하는가 | 판단 | 이유 |
| --- | --- | --- | --- |
| 워커·검증자 시행착오 회고 | 끝난 작업의 기록에서 일하는 법과 실패를 건진다 | 가장 적합 | 지금 어디에도 남지 않는 유일한 것이다. 사람이 손으로 하던 일이기도 하다 |
| 규칙의 제거 시험 수치 내기 | `rules-and-enforcement.md`의 제거 시험 가운데 대화 기록을 세어야 하는 항목을 실제로 센다 | 적합 | 회고와 같은 재료를 쓴다. 지금은 세는 사람이 없다 |
| 쌓인 기록 정리 | 결정 기록·진행 기록의 정리본을 만든다 | 일부 적합 | dreaming의 정리자만 가져오면 된다. 대화 기록이 필요 없어 싸고 안전하다 |
| 기능 상태 메모 | 코드가 무엇을 하는지, 어느 작업에서 무엇을 고쳤는지 적는다 | 맞지 않는다 | 코드와 테스트가 기준이다. 시험 실행 메모에서 뽑은 90줄 중 52줄이 이 종류였고, 한 줄은 이미 코드와 어긋나 있었다 |
| compact·`/clear` 인계 | 작업 도중의 위치를 넘긴다 | 맞지 않는다 | dreaming은 끝난 세션만 읽는다. 작업 상태 파일과 hook이 이미 맡고 있다 |
| 검증자에게 지난 지적 넘기기 | 검증 서브에이전트가 메모를 읽는다 | 맞지 않는다 | 검증자는 `[배정]` 원문만 받아야 작성자와 앞 판단에 묶이지 않는다 |
| 지식 위키 | 문서 묶음을 위키로 만들어 질문에 답한다 | 맞지 않는다 | 하네스 문서는 작고 자주 바뀌며 이미 `index.md`로 나뉘어 있다. 자료의 본전은 질문 약 240개다 |

## 왜 회고인가

### 빈 곳이 거기 하나다

하네스는 "지금 하는 일"을 커밋, 상태판, 작업 상태 파일로 빈틈없이 남긴다. "해 보고 알게 된 것"은 Orchestrator가 본 만큼만 결정 기록에 남는다. 워커와 검증자가 혼자 겪고 넘어간 일은 `/clear`와 함께 사라진다.

jobtailor에서 잰 예다.

- zsh에서 `echo ====`가 오류를 내는 일은 11일 동안 159개 세션 중 78개에서 되풀이됐다.
- 새 worktree에 `.venv`가 없어 헤맨 일, `herdr-report`를 `timeout`으로 감싸 보고가 사라진 일은 결정 기록에 없다.
- 새 worktree에 `node_modules`가 없어 보고 관문이 실패한 일은 다섯 번 겪은 뒤에야 고칠 후보가 됐다.

### 하네스가 이미 손으로 하고 있다

`rules-and-enforcement.md`의 규칙 여럿은 실제로 돌린 작업을 뒤에 분석해서 나왔다(zip-viewer의 검사 기록, 검증 왕복, 대기 사례). 2026-11-11에도 워커 세션을 손으로 재서 함정 13가지를 찾았고, `worker.md`에 여섯 가지, jobtailor의 `AGENTS.md`에 일곱 가지를 넣었다.

시험 실행에서 dreaming 분석기는 2026-11-09 하루치 기록만 읽고, 이 손 작업이 찾은 13가지 중 11가지를 메모에 적었다. 사람이 재지 않아도 같은 것이 나온다.

### 하네스의 구조와 맞는다

dreaming을 돌리는 데 필요한 것이 이미 있다.

| 필요한 것 | 하네스에 있는 것 |
| --- | --- |
| 끝난 세션의 대화 기록 | 세션 장부(`sessions.tsv`)가 역할·세션·기록 경로를 남긴다 |
| 작업의 시작과 끝 | `received.tsv`와 `reports.tsv`에 `[배정]`·`[완료]` 시각이 있다 |
| 믿을 수 있는 결함 기록 | `verify/` 검증 기록, `verdicts.tsv`, 검사 로그 |
| 정해진 모델로 헤드리스 세션 띄우기 | `herdr-verify`가 `claude -p`·`codex exec`를 띄운다 |
| 끝났다는 신호 | Orchestrator의 완료 선언과 정산(8절) |

## 어떻게 꽂는가

- 먼저 스크립트로. 오류로 표시된 도구 결과를 세는 일은 모델 없이 된다. zsh 실수는 이 방법으로 찾았다. 회고는 스크립트가 못 보는 것, 곧 오류로 표시되지 않은 헛걸음과 검증 지적에서 나온 교훈을 맡는다.
- 때. 묶음이 끝나 Orchestrator가 정산한 뒤에 돌리거나, 사용자가 손으로 돌린다. 자료처럼 매일 밤 cron으로 돌릴 이유는 없다. 하네스는 사용자가 목표를 줄 때만 돌고, 끝난 작업만 읽으면 된다.
- 단위. 기록은 작업 단위로 자른다. `[배정]`에서 다음 `[배정]`까지가 한 단위다. 워커 세션 하나의 기록은 중앙값 500KB, 큰 것은 3MB를 넘어 분석기 하나가 한 번에 읽지 못한다.
- 범위. 분석기에게 일하는 법과 실패만 적게 한다. 기능의 동작, 커밋별 경과, 판정 수치는 적지 않게 한다. 그런 내용은 코드와 진행 기록에 이미 있다. 시험해 보니 내용은 바뀌지만 양은 거의 줄지 않았다(476KB에서 385KB). 양을 줄이려면 단위마다 적을 줄 수를 정하는 식의 장치가 더 필요하다.
- 되풀이 목록. Orchestrator 4절의 "같은 실수 지적이 두 번 나오면 구조·타입·린트·테스트로 막는다"에 넣을 후보다. Orchestrator는 자기가 본 보고 안에서만 되풀이를 센다. 여러 세션에 걸친 되풀이는 이 목록에서 찾는다.
- 작업 메모. 읽는 세션은 고치지 못하게 한다. 세션 시작 hook으로 넣지 않고, 워커가 `[배정]`을 받은 뒤 목차에서 관련 파일만 연다.
- 승인. 메모에서 `AGENTS.md`나 스킬로 올리는 것은 사용자가 정한다. dreaming이 지침 파일을 직접 고치지 않는다. 시험 실행의 메모에는 틀린 줄이 섞였고(확인한 42줄 중 3줄), 하나는 하네스 규칙과 어긋나는 행동을 지침처럼 적었다.

## 기대해도 되는 것과 안 되는 것

| 기대 | 판단 | 잰 값 |
| --- | --- | --- |
| 하네스·프로젝트의 숨은 결함을 찾는다 | 된다 | 손으로 찾은 13가지 중 11가지를 하루치 기록에서 찾았다. 범위를 좁힌 실행은 12가지 |
| 도구 오류를 줄인다 | 조금 | 오류는 호출의 1.9%뿐이다. 다음 날 오류 68건 중 메모에 답이 있던 것은 28~30건이고 그중 21건은 같은 셸 실수다 |
| 검증 재작업을 줄인다 | 알 수 없다 | 차단 결함 47개 중 24개는 같은 작업 안의 재지적이라 세션 사이 기억과 무관하다. 다른 작업에서 되풀이된 것은 15개이고 대부분 한 영역이다 |
| 새 세션이 덜 헤맨다 | 재지 못했다 | 메모를 준 세션과 안 준 세션을 견줘야 안다 |
