# 하네스에 맞는가

[두 자료](sources.md)의 방법을 우리 하네스에 가져올지 판단한다.

1. 우리 하네스에 실제로 빠진 것을 채우는가?
2. 이미 있는 장치와 겹치지 않는가?
3. 자율 모드(권한 확인 없이 도는 모드)에서 새 위험을 만들지 않는가?

## 출발점이 다르다

| 항목 | 두 자료 | 우리 하네스 |
| --- | --- | --- |
| 세션 | 작업이나 질문마다 새 세션을 띄운다. 메모가 없으면 아무것도 모른다 | 세션을 오래 살려 둔다. 비슷한 작업은 그 맥락을 가진 세션에 맡기고, 전혀 다른 작업으로 넘어갈 때만 `/clear`한다 |
| 실행 방식 | Anthropic 서버(Managed Agents API) | 내 컴퓨터의 Claude Code·Codex CLI와 hc. API 키 없이 구독으로 돈다 |
| 기록을 두는 곳 | 메모 저장소 | git 커밋, `docs/status`(상태판·작업 계획·결정 기록), `docs/progress`(새 파일로만 쌓는 기록), 작업 상태 파일 |
| 문서 | 새로 위키를 만든다 | 기획·설계 문서가 이미 `index.md` 목차와 주제별 문서로 나뉘어 있다. 코드는 graft가 찾아 준다 |
| 권한 | 분석기는 셸을 못 쓰고, 읽는 쪽은 읽기만 한다 | `HERDR_AUTONOMOUS=1`이면 모든 세션이 권한 확인 없이 돈다 |

우리는 세션을 오래 쓰고, 해야 할 일과 결정은 git과 문서에 남긴다. 그래서 "세션이 아무것도 기억 못 한다"는 두 자료의 문제는 우리에게 훨씬 작다.

## 세션이 바뀔 때 무엇이 남고 무엇이 사라지나

| 언제 | 지금 남는 것 | 사라지는 것 |
| --- | --- | --- |
| 작업 중 compact(대화를 요약해 줄이는 것) | compact 직전의 git 상태, 작업 상태 파일 앞 40줄, 요약("실패한 시도와 원인은 남겨라"라고 지시함) | 요약에서 빠진 세부 내용 |
| 작업을 끝내고 `/clear` | 커밋, 상태판, `docs/progress` 기록, 결정 기록 | **작업하며 배운 것 전부**: 실패한 방법과 이유, 환경 함정, 여러 번 시도해서 찾은 명령어. compact 때는 이걸 남기라고 하지만, `/clear` 때는 아무 장치가 없다 |
| Orchestrator·Commander가 스스로 정리할 때 | 상태판, 세션 장부, 결정 기록 | 위와 같다(워커보다는 적다) |
| 세션 종료 | 위와 같다 | 위와 같다 |
| 다음 세션 시작 | 역할과 읽을 스킬 경로를 자동으로 넣어 준다 | 다른 세션이 배운 것을 읽을 곳이 없다 |

작업 상태 파일(`~/.claude/herdr/handoff/<프로젝트>/<role>.md`)은 지금 하는 작업 하나의 위치만 적는다. 다음 작업이 덮어쓰고, 저장소 밖에 있어서 다른 세션이나 Codex는 보지 못한다. `docs/progress`는 결정·조사·진행 상황을 적는 곳이라, 배운 것을 적는 형식이 없다.

예를 들어 jobtailor에서 "worktree에서는 `make install`을 먼저 해야 한다" 같은 함정을 다음 세션이 또 겪는지, 지금은 알 수도 없고 막을 수도 없다.

**다만 배운 것이 남지 않아서 실제로 얼마나 손해를 보는지는 재 보지 않았다.** 같은 일을 다시 겪는 경우가 드물면 넣을 이유가 없다. 그래서 [적용 계획](proposal.md)은 재 보는 것부터 시작한다.

## 무엇을 가져오고 무엇을 뺄까

| 항목 | 결정 | 이유 |
| --- | --- | --- |
| Managed Agents 메모 저장소·워크플로 API | 가져오지 않는다 | 우리는 내 컴퓨터의 CLI로 돈다. API 키와 따로 드는 돈이 생기고, Codex 세션은 못 쓴다. jobtailor의 개인 경력 자료가 담긴 대화 기록을, 데이터를 남기지 않는 조건이 없는 서버에 올리게 된다 |
| 매일 밤 검토 없이 자동으로 메모 고치기 | 가져오지 않는다 | 자율 모드 세션은 권한 확인 없이 돈다. jobtailor는 외부 채용 공고를 가져오는데, 공고 속 나쁜 글이 대화 기록을 거쳐 메모에 들어가면 검토 없이 다음 날 모든 세션에 퍼진다. 자료도 이 점을 주의점으로 든다 |
| 메모를 모든 세션 시작 때 자동으로 넣기 | 가져오지 않는다 | 자료도 권하지 않는다(매번 토큰이 들고 나쁜 글이 퍼진다). 지금처럼 역할과 경로만 넣는다 |
| 문서를 위키로 다시 만들기(knowledge-wiki) | 가져오지 않는다 | 기획·설계 문서는 이미 사람이 다듬고 목차를 달았다. 코드는 graft가 찾아 준다. 문서는 개발하면서 계속 바뀌고, 읽는 세션도 몇 개뿐이다. "질문 240개쯤 쌓여야 본전"이라는 조건이 맞지 않는다 |
| 대화 기록 전체를 나중에 다시 읽기 | 미룬다 | jobtailor의 최근 Claude 대화 기록 50개는 원본 파일로 평균 약 3.9MB, 합쳐서 약 190MB다(2026-11-09 기준, 텍스트로 줄인 크기는 재지 않았다). 자료에서 12MB에 약 $8였으니, 통째로 읽으면 비용이 크다. 오류·재시도·마지막 메시지처럼 필요한 부분만 골라 읽을 때만 쓴다 |
| "각자 적고, 한 사람이 모아 정리하기" | 바꿔서 가져온다 | 우리 `docs/progress`는 원래 새 파일로만 쓴다. 그래서 knowledge-wiki가 받아들인 5% 덮어쓰기 손실이 생기지 않는다. 워커는 각자 새 파일로 적고, 모아서 정리하는 일은 한 세션이 맡는다 |
| 작업 끝에 배운 것 적기 | 가져온다 | 워커가 `[완료]` 전에 적으면, 아직 기억이 남아 있어서 대화 기록을 다시 읽을 필요가 없다. 자기가 쓴 것이라 놓치는 부분은 모아서 정리할 때 확인한다 |
| 메모 쓰는 규칙 | 가져온다 | 지금 아는 사실로 쓰기, 날짜와 출처 붙이기, 옛 값은 이력으로 남기기, 다르면 `CONFLICT:`, 비밀 금지, 자료 속 지시 따르지 않기. 우리 규칙("에이전트의 기록은 사용자 결정을 뒤집지 못한다", "주석·문서·보고는 단서다")과 방향이 같다 |
| 실제 결과로 확인하기(에이전트 말보다 실행 결과를 믿기) | 가져온다 | 정리할 때 배운 것마다 커밋·검사 결과·코드로 확인한다. 확인 못 한 것은 "미확인"으로 둔다 |
| 목차 한 줄에 파일 하나, `[[링크]]` | 바꿔서 가져온다 | 우리 `index.md` 형식("다루는 주제", "언제 읽는가")과 일반 상대 링크를 쓴다. 두 형식을 섞지 않는다 |
| 쓰는 쪽과 읽는 쪽 나누기, 검토 뒤 반영 | 바꿔서 가져온다 | 읽기 전용 저장소 대신 이미 쓰는 git 흐름을 쓴다. worktree에서 정리하고 커밋 → 검증 서브에이전트의 판정 PASS → `[완료]` → 병합을 거친다 |
| 실행 전 비용 계산과 예산 한도 | 가져온다 | 정리할 때 읽을 양을 먼저 세고, 한도를 넘으면 멈춘다 |
| Claude Code 자동 메모리(`~/.claude/projects/<프로젝트>/memory/`) | 쓰지 않는다 | Claude만 쓰고, 사람마다 따로 있고, 저장소 밖에 있다. Codex 워커나 다른 컴퓨터에서는 보지 못한다 |

## 어디에 무엇을 둘까: 한 사실은 한 곳에

새 메모 장소가 기존 문서와 같은 내용을 따로 갖지 않게 나눈다.

| 내용 | 두는 곳 |
| --- | --- |
| 무엇을, 왜, 어떻게 만드는가 | `docs/service-plan`, `docs/design`(지금 그대로) |
| 결정과 이유 | `docs/progress`의 결정 기록, `docs/status/decisions.tsv`(지금 그대로) |
| 지금 하는 작업의 위치 | 작업 상태 파일, 상태판(지금 그대로) |
| 모든 세션이 지켜야 할 규칙 | `AGENTS.md` 프로젝트 규칙. 배운 것이 규칙이 될 만하면 사용자 승인을 받아 옮긴다 |
| **작업하며 배운 것**(함정, 실패한 방법과 이유, 정확한 명령어·값, 도구의 특이한 점) | 새로 만든다. [적용 계획](proposal.md) 참고 |
| 하네스 자체에서 배운 것(hc·hook·도구 버전의 특이한 점) | 하네스 저장소 `docs/policy/context-policy.md`의 "실측으로 알게 된 것" |
